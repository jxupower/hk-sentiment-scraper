# requirements.lock — generation + upgrade workflow

**Purpose**: `requirements.lock` is a fully-pinned, hash-checked artefact
derived from `requirements.txt`. It gives the Docker image and CI reproducible
installs — the same lockfile → the same wheels → the same image digest.

**Compliance context**: closes P1.5 of the July 2026 compliance assessment
(see [compliance_assessment.md](compliance_assessment.md) §5). Maps to
CIS Controls v8 §2 (Software Inventory), OWASP ASVS 5.0 V10 (Malicious
Code / supply chain), ISO 27001:2022 A.8.30.

**Who edits what**:
- **You edit** `requirements.txt` — human-friendly floor pins with rationale
  comments. This is the source of truth.
- **You never edit** `requirements.lock` by hand — it's a build artefact,
  regenerated by `pip-compile` and committed alongside the `requirements.txt`
  change.

## Bootstrap (one-time per developer)

```bash
python -m pip install --upgrade "pip-tools==7.4.1"
```

## Adding a package or bumping a floor pin

1. Edit `requirements.txt` — change the floor pin or add the new package
   line, and keep the rationale comment above it.
2. Regenerate the lockfile **inside a Python 3.11 container** (see
   "Foot-gun" below):

   ```bash
   docker run --rm -v "$PWD":/w -w /w \
       python:3.11-slim-bookworm@sha256:b18992999dbe963a45a8a4da40ac2b1975be1a776d939d098c647482bcad5cba \
       bash -c 'pip install --quiet "pip-tools==7.4.1" && \
                pip-compile --generate-hashes --resolver=backtracking \
                            --strip-extras --output-file=requirements.lock \
                            requirements.txt'
   ```

3. Verify the new lockfile installs cleanly against the same interpreter:

   ```bash
   docker run --rm -v "$PWD":/w -w /w \
       python:3.11-slim-bookworm@sha256:b18992999dbe963a45a8a4da40ac2b1975be1a776d939d098c647482bcad5cba \
       bash -c 'pip install --require-hashes -r requirements.lock'
   ```

4. Commit `requirements.txt` and `requirements.lock` in the same commit.

## Dependabot upgrades

Dependabot's `pip` ecosystem (see `.github/dependabot.yml`) opens weekly PRs
against `requirements.lock`. Review the diff, run the verification step
above locally if the change is non-trivial, and merge. Dependabot does not
touch `requirements.txt` — it operates directly on the lockfile.

## Foot-gun: Python-version-specific lockfile

`pip-compile` resolves against the running interpreter. A lockfile generated
on Python 3.14 pins to package versions + wheel hashes that only work on 3.14.
The container runtime is **Python 3.11** (see `Dockerfile` FROM line). Always
regenerate the lockfile in a 3.11 environment — the Docker command in step 2
above is the correct target.

If you ever upgrade the container to Python 3.12+, regenerate the lockfile
inside the new base image and update the `python:3.11-slim-bookworm@…`
reference in this doc + the Dockerfile.

## Skipping the lockfile in an emergency

If you need to install a hotfix version that isn't in the lockfile:

```bash
# Local dev only — never merge without a regenerated lockfile.
pip install <package==version>
```

Any commit that changes `requirements.txt` without a matching lockfile update
will drift the container away from CI. Don't merge such a PR.
